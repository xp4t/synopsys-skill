# Validation scope

This is a reusable skill and execution framework, not a statement about tools or
licenses installed on the reader's machine. Installed products, versions, startup
requirements and readiness must be discovered and validated locally.

Framework tests cover preserved argument boundaries and executable wrapper names,
zero-exit errors, timeouts, checkpoint/input integrity, bounded retries, verification
gates, finite metrics and PPA regression decisions. These tests use temporary
fixtures and do not establish physical implementation or signoff capability.

Tcl structural checks do not prove that a vendor command exists or applies at the
current implementation stage. Read the installed documentation, verify command
availability and execute representative stages before making tool-specific claims.

Report evidence separately as:

1. Documentation-validated: exact installed syntax, restrictions and prerequisites.
2. Syntax-validated: metadata, source structure and Tcl framing.
3. Tool-executed: actual invocation with retained diagnostics.
4. Stage-validated: required artifacts, checks and metrics passed for that stage.
5. End-to-end-validated: the complete configured verification chain passed for
   the final implementation and streamed layout.

Full physical execution requires a coherent qualified technology package, suitable
licenses, methodology-specific initialization/report adapters and complete required
signoff coverage. PDK-dependent templates deliberately omit automatic success
results until the relevant evaluator is supplied.

Store installation-specific evidence and readiness reports in private local state.
Do not publish runtime logs, host/account identifiers, license settings, proprietary
manual content, technology files or confidential design artifacts with this project.
